# 仕様書：Pikkles（ピクルス）

JPHACKS 2026。実装はこの仕様に従う。迷ったらここに戻り、仕様にないことは勝手に足さない。

## 1. プロダクト概要

撮ったモノと描いたイラストだけがステッカーになり、シール帳と、その場に居合わせた人たちとの共同フィールドに貼ってコラージュでき、会ったときにプロフ交換のノリでステッカーを交換できるSNS。

- 一行ピッチ：イベントや新歓で初めて会った人とSNSを交換しても、数週間後には「どこで会った誰だっけ」となり、出会いが形に残らない。それを、会ったその場でステッカーを1枚ずつ交換し、その交換を2人それぞれのPDSに「この人とここで会った」記録として残すことで解決する。
- なぜステッカーか：名前や顔よりも、その人が選んだ好きなモノの方が記憶に残る。どれを渡すか選ぶこと自体が自己紹介になり、初対面の会話のきっかけになる。さらに背景を消してモノだけにし、位置情報も消すので、公開されるAT Protocolの上でも安心して出せる。
- ターゲット：イベント、サークルの新歓、ハッカソン、ライブなどで初めて会った人とつながる大学生。共同フィールドは、その場に居合わせた人たちの寄せ書きとして使う
- デモの場面：JPHACKSの会場そのもの。Hack Day中にほかのチームやゲストとステッカーを交換してもらい、本物の交換記録と、場面「JPHACKS 2026 東京B」の共同フィールド（会場の寄せ書き）を見せる。交換してもらう相手はBlueskyアカウントを持っている人が中心。持っていない人には、bsky.appの登録QRとPikklesのQRを並べた紙を渡す。チームの予備アカウントは貸さない（「本人のPDSに残る」という売りが崩れるため）
- 差別化の核：他人のステッカーを自分のシール帳に貼るには、対面での交換が必要

## 2. コア体験とルール

| 場所 | 役割 | 貼れるステッカー | 並び |
| --- | --- | --- | --- |
| シール帳 | 集めたステッカーを自由に貼って飾る | 自分のもの＋交換で手に入れたもの | ページ制、配置は自由 |
| 共同フィールド | メンバーが各自のステッカーを貼り合う | 各自の自分のもの＋交換で手に入れたもの（2026-10-25変更） | 1枚のキャンバス |
| タイムライン | 交換した相手と共同フィールドのメンバーの新しいステッカーと交換の出来事が流れる | （閲覧のみ） | 新しい順 |

交換のルール

1. 交換は対面のみ。相手のQRコードを読み取って始める。QRは60秒で失効して作り直す。対面であることはこれ以上は確かめない（スクショを送れば遠隔でもできる、と割り切る）
2. お互いに1枚ずつ選んで交換する
3. 共同フィールドにある他人のステッカーを自分のシール帳に持ち帰るには交換が必要
4. 交換したステッカーには「誰と・いつ・どんな場面で交換したか」が記録される。場面（例：「JPHACKS 2026 東京B」）は交換を始めた人が任意で手入力し、2人の記録に同じ値が入る。GPSなどの位置情報は使わない（2026-10-24追加）

### シール帳を「ビン」に見立てる（2026-10-24追加）

サービス名の Pikkles（ピクルス）に合わせて、自分のシール帳を、ピクルスを漬けるビンに見立てる。集めたステッカーを、漬け液の中に入れて取っておくイメージ。

1. 画面の名前と下部タブの名前は「ビン」にする。仕様の中の呼び方（シール帳）、URL（`/binder`）、Lexicon（`binder.page`）は変えない
2. ページは漬け液のような薄い緑のグラデーションにし、泡を浮かべる
3. 貼ったステッカーは、液体に浮いているように、ゆっくり上下にぷかぷか揺らす。1枚ずつ揺れの速さと始まりをずらす
4. 揺れは表示だけ。保存する配置（`binder.page` の x・y・拡大・回転）には入れない。触っている（選んでいる）ステッカーは揺らさない
5. 端末で「視差効果を減らす」（`prefers-reduced-motion`）がオンなら揺らさない
6. 共同フィールド（S8）のキャンバスは今までどおりで、揺らさない

## 5. データ設計（AT Protocol）

- ユーザーのデータはすべて本人のPDSに保存する。自前サーバーは集計と交換の仲介だけ
- MVPではすべて公開データ
- PDSへの書き込みはブラウザ側（公式SDK）のみ。Pythonサーバーは他人のPDSを読むだけ
- 参照は strongRef（`uri` + `cid`）

NSID：`com.kosora623.pikkles.*`（アプリは `pikkles.kosora623.com` で公開）。PDSに書き始めたら変えない。以下では `app.<ns>` と書く。

```text
app.<ns>.sticker          ステッカー本体（rkey: TID）
  image      blob      切り抜き済み透過PNG。最大1MB（/cutout で長辺を1024pxに縮めてから切り抜く）
  width      int
  height     int
  source     string    "photo" または "illustration"
  caption    string    任意、最大100文字。ピクルス名（2026-10-25に一言から変更）
  createdAt  datetime  撮影日時（イラストは保存日時）

app.<ns>.binder.page      シール帳の1ページ（rkey: ページ番号）
  placements[]
    sticker   strongRef
    x, y      int       中心の位置。幅・高さを10000とした値。はみ出しを許して -2000〜12000
    scale     int       1000で等倍。100〜5000（0.1倍〜5倍）
    rotation  int       度（時計回り）。-180〜180
    z         int       重なり順。0以上、大きいほど上
  updatedAt  datetime

app.<ns>.exchange         交換の記録（2人がそれぞれ自分のPDSに書く）
  sessionId  string    最大128文字
  occasion   string    任意、最大50文字。交換した場面（手入力。位置情報ではない）
  message    string    任意、最大100文字。この交換で相手に渡す一言（2026-10-25追加）。成立の照合には使わない
  partner    did
  gave       strongRef  自分が渡したステッカー
  received   strongRef  受け取ったステッカー
  createdAt  datetime

app.<ns>.field            共同フィールド（作った人のPDS）
  title（最大50文字）, createdAt

app.<ns>.field.member     参加の記録（参加者のPDS）
  field (strongRef), createdAt

app.<ns>.field.placement  共同フィールドへの貼り付け（貼った人のPDS）
  field (strongRef), sticker (strongRef, 自分のもの、または成立した交換で受け取ったもの), x, y, scale, rotation, z, createdAt
  （受け取ったものは、貼った人と作った人の PDS に対になる exchange があるかで確かめる。6章の成立条件1〜4と同じ中身）
  （x, y, scale, rotation, z の単位と範囲は binder.page の placements と同じ）

app.<ns>.want             「ほしい」
  subject (strongRef), createdAt
```

Lexiconの定義ファイル（JSON）は `lexicons/`、TypeScriptの型は `frontend/src/lexicon-types.ts` にある（2026-10-24作成）。

数値は整数で持つ（2026-10-24変更）：AT Protocolのデータに小数は入らないため、位置・拡大率・回転は上のとおり単位を決めた整数にする。「最大◯文字」は書記素の数（`maxGraphemes`）で数え、バイト数の上限（`maxLength`）はその10倍にする。

交換が保証するもの：画像の所有権ではなく、「このアプリで自分のシール帳に貼れる権利」と「誰と交換したかという記録」。

## 6. 交換の仕組み

1. Aが場面（任意）を入力してセッションを開始し、QRを表示（QRの参加URLは60秒で失効し、画面上で自動的に作り直す）
2. BがQRを読んで参加。参加の画面に場面が表示される。Bが未ログインならログインしてからこの画面に戻る。Bの手持ちが0枚なら、撮影→ステッカー化をその場で行い、そのまま3の選択に進む
3. 2人がそれぞれ1枚選んで確定（WebSocket）
4. サーバーが両者確定の合図を送る
5. 2人がそれぞれ自分のPDSに `exchange` レコードを書く（`occasion` はサーバーが持つセッションの値をそのまま入れる）
6. 2人がそれぞれ書いたレコードのURIをサーバーに通知
7. サーバーが2人のPDSからレコードを読んで照合
8. 照合が通れば成立を通知

成立の条件（7で確認）

1. 2人のPDSに同じ `sessionId` の `exchange` がある
2. 互いの `partner` が相手のDIDである
3. Aの `gave` = Bの `received`、Bの `gave` = Aの `received`
4. `gave` のステッカーが本人のPDSにある本人のもの
5. 2人の間にBlueskyのブロック（`app.bsky.graph.block`）がどちら向きにも無い。2人それぞれのPDSの `app.bsky.graph.block` を `listRecords` で読み、相手のDIDが `subject` に無いことを確かめる（セッションへの参加時にも確認する）
6. 2人の `occasion` が、サーバーが持つセッションの値と同じ（入力が無いときは2人とも空）

失敗時

| 状況 | 扱い |
| --- | --- |
| 3で片方が選ばずに閉じた | 3分でセッション破棄、もう片方に「キャンセルされました」 |
| 5で片方だけが書いた | 成立とみなさない。書いた側に「相手の記録待ち」 |
| 7で内容が対応しない | 成立とみなさず、シール帳に貼れない |

## 7. タイムライン

本線は「相手のPDSを直接読む」方式。相手は数人しかいないので、全体を購読しなくて足りる。Jetstreamによる収集は、間に合えば足す（後述）。

1. 表示する相手は「成立した交換の相手」と「同じ共同フィールドのメンバー」。どちらもサーバーのPostgresに持つ（交換は成立判定のとき、メンバーは招待からの参加のときに記録する）
2. タイムラインAPIは、その相手それぞれのPDSから `app.<ns>.sticker` と `app.<ns>.exchange` を `listRecords` で読み、新しい順に混ぜて返す。交換は成立したものだけ
3. 削除されたレコードはPDSから消えているので、読み直せば自然に出なくなる。削除されたステッカーはタイムライン・シール帳・共同フィールドに表示しない（strongRefの先が読めなければ表示しない）
4. ログイン中のユーザーとブロック関係にある人の出来事は返さない。ブロックは6章の成立条件5と同じく、2人のPDSを `listRecords` で読んで確かめる
5. 読み込みは相手ごとに短い時間（例：30秒）キャッシュする

間に合えば：収集プロセスがJetstreamに接続し、`wantedCollections` を自分たちのコレクションに絞ってPostgresに保存する。cursorも保存し、再起動時はそこから再開する。`app.bsky.graph.block` は全ユーザー分が流れて重いので購読しない

### 共同フィールドのリアルタイム反映（2026-10-24追加）

開いている共同フィールド（S8）に、ほかのメンバーの貼り付け・移動・削除を、リロードしなくても反映する。

1. ブラウザが公開のJetstream（`wss://jetstream2.us-east.bsky.network/subscribe` など。つながらなければ別のホスト）に直接つなぎ、`wantedCollections=com.kosora623.pikkles.field.placement` で購読する。サーバーを通さないので、Renderが寝ていても動く
2. 受け取った `field.placement` のうち、開いているフィールドを指し、メンバーが自分のステッカーか交換で受け取ったステッカーを貼ったものだけを反映する（PDSから読むときと同じ条件）。知らない人のものが来たら、メンバー一覧を読み直す（新しく参加した人の場合）
3. 他人の移動が見えるのは、その人が手を離して保存したあと（S8は動かし終わって1秒後に保存する）。ドラッグ中の動きは配らない
4. Jetstreamの中身は署名を確かめていないので、PDSを正とする。30秒ごと、Jetstreamをつなぎ直したとき、画面に戻ったときに、メンバー全員のPDSから読み直して正す。自分の貼り付けは画面の状態を正とし、保存待ちの動きを消さない

## 8. バックエンドAPI（下書き）

| メソッド | パス | 用途 | 入力 | 出力 |
| --- | --- | --- | --- | --- |
| POST | `/cutout` | 切り抜き・白フチ・影 | 画像（multipart） | JSON：`image`（base64の透過PNG）、`width`、`height`。長辺を1024pxに縮めてから処理し、1MBに収める |
| POST | `/exchange/sessions` | 交換セッション開始 | `occasion`（任意） | `sessionId`、QR用URL |
| POST | `/exchange/sessions/{id}/join` | 参加 | なし | セッション状態 |
| WS | `/exchange/sessions/{id}/ws` | 選択・確定の同期 | strongRef、確定 | 相手の選択、確定状態 |
| POST | `/exchange/sessions/{id}/commit` | 交換記録を書いたことの通知 | 記録のURI | 成立判定の結果 |
| GET | `/timeline` | タイムライン | `cursor`、`limit` | 出来事一覧 |
| POST | `/fields/invite` | 共同フィールドの招待（メンバーだけ） | `field`（strongRef） | `code`（6文字、10分で失効。QRにも同じものを載せる）、`expiresIn` |
| POST | `/fields/invite/lookup` | 参加コードからフィールドを引く | `code` | `field`、`expiresIn`。違うコードは1人10分に10回まで（超えると429） |
| POST | `/fields/join` | 共同フィールドに参加 | `field`、`code`（すでにメンバーの人と作った人は不要） | メンバー一覧 |

成立した交換は2人の PDS から読む（サーバーは持たない）。

WebSocketメッセージ（案）

```text
→ {"type": "auth", "token": "…"}
→ {"type": "select", "sticker": {"uri": "at://…", "cid": "…"}}
→ {"type": "confirm"}
← {"type": "partner_selected", "sticker": {…}}
← {"type": "both_confirmed", "occasion": "…"}
← {"type": "completed", "exchange": {…}}
← {"type": "cancelled", "reason": "…"}
```

認証：AT Protocolのサービス認証（service auth）を使う。OAuthのトークンはDPoPで縛られていてサーバーに渡しても使えないため。

1. ブラウザが、ログイン中のセッションで本人のPDSの `com.atproto.server.getServiceAuth` を呼ぶ。`aud` はバックエンドのDID（`did:web:<バックエンドのホスト名>`）
2. 返ってきた短命のJWTを、HTTPは `Authorization: Bearer` で、WebSocketは接続直後の最初のメッセージ `{"type": "auth", "token": "…"}` で送る
3. サーバーは `iss` のDID文書から署名鍵を引いてJWTの署名を検証し、`aud` と有効期限を確かめる。Pythonの `atproto` パッケージの検証関数を使う
4. バックエンドは `/.well-known/did.json` で自分の `did:web` を公開する
5. OAuthのscopeで `getServiceAuth` が許可されるかは、骨組みの段階（0〜3時間）で確かめる。通らなければ `transition:generic` のscopeにする

Hack Dayのデプロイ先はRender（無料、カード不要）。そのため次のように運用する。

- DBはRender Postgres（無料、作成から30日で期限切れ）
- 収集プロセスを足す場合は、Webサービスの中で起動する
- 無料版は15分アクセスがないと止まり、次のリクエストに数十秒かかる
- 背景除去は軽量モデル（`u2netp` など）。RMBG系は非商用ライセンスなので使わない
- デプロイはGitHub Actions（`.github/workflows/deploy.yml`）。frontendはVercel CLI、backendはRenderのDeploy Hook

安心のための実装上の決まり

- 画像は切り抜き後にPNGで再エンコードし、EXIFを含むメタデータを残さない。アップロードしたイラストも同じく再エンコードする
- OAuthで要求する権限には、自分たちのコレクション（`com.kosora623.pikkles.*`）、画像のアップロード、`app.bsky.graph.follow`（要件13を作る場合）を含める
